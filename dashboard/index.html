❓ What does everything on this dashboard mean?

Banners at the top (what the colors mean)

Grey — a check flagged something, but real requests are succeeding right now, so it's informational: read it when you have a minute, nothing to do urgently. Darkbloom's own doctor tool has produced known false positives (its RAM-fit check in particular), which is why those land here rather than in yellow. Yellow — something is actually off (trust not hardware-level, power sampling not running, running hot, serving paused by Price Guard) and the banner says what to check. Red — a model-load error within the last two minutes; if requests keep failing, that's the one to look at first.

Top summary cards

Network trust — whether Darkbloom's coordinator (the server that hands out work) trusts this Mac enough to send it paid jobs. "Trusted — receiving jobs" (raw value hardware) is what you want. "Online, not trusted yet" (raw self_signed) means connected but receiving nothing - on this network it's usually a temporary flicker on Darkbloom's side that clears in minutes, and you get a macOS notification either way. The raw coordinator string is shown under the label for anyone debugging with Darkbloom support.

Provider — the `darkbloom` background program that actually serves requests. "Serving a request now" is read from its own live state file (pulsing dot). "Running, waiting for jobs" is the normal state most of the time - you still earn the base reward while trusted and idle.

Requests — requests served and tokens processed since the provider last (re)started. This resets on every restart, so it's not a lifetime total; lifetime numbers are in the Darkbloom Account panel.

Warm models — how many models are currently loaded in memory (instant response) vs. how many are downloaded to disk in total.

Accumulated electricity cost and Net — see the calculation explainer under the cost/revenue chart further down for the exact formula.

Live Power gauges

CPU / GPU / Total — CPU and GPU are instantaneous draw straight from `powermetrics`, ~5 times per second. "Total" is the whole Mac: if macmon is installed it's the real reading from the Mac's own SMC power sensor (RAM, SSD, fans and all) divided by an assumed 90% power-supply efficiency, i.e. close to what a wall meter would show. Without macmon it's CPU+GPU plus a flat 7W guess - measured on an M4 Pro Mac mini (no peripherals attached) that guess is roughly right at idle but about 2.5x too low under sustained inference: the SMC reported ~60W while CPU+GPU+RAM rails summed to ~29W. Install macmon (brew install macmon) if you care about the cost numbers at all.

RAM used — system-wide memory pressure, not just this app's usage. Turns red/orange as it approaches full, since that's the exact condition that caused real model-load failures during testing.

GPU Headroom — how much of the GPU is not busy right now, straight from powermetrics. Idle Macs sit around 75-85% (the OS itself uses some); it drops toward 0% during real inference. Low is expected while serving, not a problem.

Fan Speed / GPU Temp — read via darkbloom fan status (Apple Silicon doesn't expose either through powermetrics). Temp turns orange at 85°C and red at 95°C. If the GPU is hot but the fan is barely spinning, a banner appears at the top: that means Darkbloom's own fan-control helper isn't engaging. It isn't dangerous (macOS throttles the chip before any damage) but it costs performance - the small text under the gauge shows the helper's current mode.

Utilization (last hour) — average GPU busy-ness over the last ~60 minutes, from the same powermetrics figure as GPU Headroom, logged every 5 minutes. A low or 0% reading with a healthy Trust/Daemon status just means genuinely little traffic right now, not a fault — that's when the base-reward floor is what's paying (see Nerdy Stats).

Darkbloom Account (real payout vs. our own estimate)

Real jobs/tokens/payout per model, pulled directly from Darkbloom's own API every 30 seconds - the same device token `darkbloom login` already stores locally, no browser step needed. The "Darkbloom gap" column compares what this dashboard's own rough flat-rate guess would have paid for the same tokens against what Darkbloom's ledger actually paid — it is not an official platform fee or a claim about Darkbloom's pricing. It's just a check on our own estimate's accuracy, and our simplistic single blended rate (not split by input/output pricing) is probably the thing that's actually off.

Nerdy Stats

Average prompt/completion length is computed from the same real earnings entries as the Account panel above, excluding base_reward floor-payment rows (which always carry zero token counts and would otherwise skew the average toward zero). Request duration is not data from Darkbloom at all - it doesn't expose timing anywhere - so a background thread here watches the daemon's own inference_active flag flip on and off, twice a second, and logs how long each "on" window lasts. It only starts counting from whenever this dashboard first started running, and can undercount requests shorter than the check interval. GPU memory active/cached and KV-backend/MTP settings come straight from the daemon's own state file. Health checks are `darkbloom doctor`'s own findings, refreshed every 5 minutes since doctor makes a real network call - anything doctor reports as a FAIL also shows up as a banner at the top of the page (shown as a caution, not a confirmed outage, since this exact check has been observed to be wrong before). Note: neither this dashboard nor Darkbloom's API expose actual prompt or response text anywhere — only token counts, which is what's shown.

Warmup

Periodically sends a tiny request to the provider's local endpoint to keep the active model loaded in memory, so it's ready instantly instead of needing to reload when the first real request of the day arrives.

Disk Usage

Every model `darkbloom` has downloaded, with size and whether it's the one currently active. Darkbloom downloads these on its own as the network assigns models to this Mac, so ending up with several is normal. Unused ones only cost disk space and are safe to remove - darkbloom re-downloads a model if it's ever assigned again. Models not currently in use get a one-click "copy remove command" — this dashboard never deletes files itself, it only prepares the exact command for you to run.

Charts

Power history — the same wattage as the live gauges, logged every 5 minutes so you can see trends over hours/days. Once there's enough history to need downsampling, a faint dashed "peak" line appears alongside the average — the highest single reading inside each plotted bucket, so brief spikes stay visible even when hundreds of raw samples are compressed into one line.

Real Earnings vs. Electricity Cost (last 48h) — the one chart to trust for "am I making money": every real ledger entry Darkbloom paid (including the base reward) added up, against the measured electricity cost added up, over the last two days. Both real, both USD. Builds up locally over ~2 days of dashboard uptime because Darkbloom's API only returns the most recent batch of entries.

Estimated cost vs. revenue (folded away, nerdy) — two older charts using a rough local revenue guess (tokens × a flat rate) over the full logged history. They ignore the base reward, so they look far worse than reality; kept only for the long-range token-earnings trend.

Electricity Price & Profitability — the actual price per kWh, yesterday through tomorrow, from the source you pick (Sweden, Norway, any European bidding zone, UK Octopus Agile, US ComEd, or a flat rate). The right-axis "Net" overlay is real earnings minus real cost per 15-minute slot - so you can see which hours of the day are actually worth running. Picking a source/zone here changes every price-related number on the page, including cost tracking from that moment on.

Ollama indicator

Only shown if Ollama (another program for running local AI models) is installed on this Mac. It flags when Ollama has a model loaded in memory at the same time, since that competes for the same unified memory as the Darkbloom provider and caused real crashes during testing on a 48GB Mac. If you don't have Ollama, you won't see this at all.

How is the electricity cost calculated?

Electricity price: the source and zone you picked in the Electricity Price panel below, re-checked every 15 minutes - the actual price for the current hour, not an estimate. Prices arrive in that source's currency and are converted to USD (rate checked hourly) so everything on this page shares one currency.

Power: every 5 minutes the Mac's average power draw is turned into the energy used in that slice and priced at that slice's own rate. If macmon is installed, power is the whole-system reading from the Mac's own SMC sensor (RAM, SSD, fans included) divided by an assumed 90% power-supply efficiency to approximate the wall. Without it, it's CPU+GPU from powermetrics plus a flat 7W guess - which measured about right at idle but roughly 2.5x too low under sustained inference on an M4 Pro Mac mini (SMC ~60W vs. rails ~29W, nothing plugged into the ports). The footer at the bottom of the page says which method is in use. Rows logged before macmon was in use keep their old, lower numbers.

Net (real balance) at the top = your real account balance minus this accumulated cost.

Estimated cost vs. revenue over full history (nerdy — will NOT match the Net card, read why)

These two charts use a rough local revenue guess (tokens × a flat rate) that ignores the base reward - which is most of the real income - so they read far more pessimistic than your real balance. They're kept because they cover the full logged history (the real ledger only covers ~2 days locally) and show the token-earnings trend. For "am I making money", use the Net card and the real 48h chart above instead.
